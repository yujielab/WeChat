# Cuven 质量标准与验收门槛（最高决策权）

本文件是全组统一的思路和"完成"的定义。任何改动合入 `master` 前都必须满足下列要求；有冲突时以本文件为准，本文件没写到的由最高决策权在群里拍板。

## 一、统一思路（产品原则）
1. **聊天优先**：发消息、看消息永远是最快的路径；任何新功能都不能让这条路径多一步或变慢。
2. **状态永远可见**：发送中、已发送、失败、离线、重连，每个状态都必须有清楚的视觉表达和恢复方式，不能静默失败。
3. **一种问题只用一套方案**：先复用现有组件和 class（如 `.offline-banner`、`.quote`、`confirmAction`），不另起炉灶。
4. **Apple 原生质感**：遵守 `docs/hig-audit.md`：字号层级、44pt 点击区域、对比度 ≥ 4.5:1（大字 ≥ 3:1）、浅色/深色模式都要正确、尊重"减弱动态效果"。
5. **iPhone Duo 双形态**：折叠和展开两种形态、左右安全区都必须正确，不能只测一种。
6. **克制**：动效服务于反馈，时长 150–350ms，用现有弹簧曲线；不加装饰性动画。

## 二、完成的定义（每个提交都要满足）
- [ ] 先把最新的 `master` 合进自己的分支，Node 22 下 `npm test` 全部通过；新功能要补测试。
- [ ] 浅色、深色 × 折叠、展开，四种组合的截图放进 `docs/screenshots/<分支名>/`，涉及改版的附前后对比。
- [ ] 读屏可用：按钮有可读的名称，切换类控件带 `aria-pressed` 或 `aria-checked`，焦点顺序合理。
- [ ] 空状态、加载、出错、离线四种情况都处理过。
- [ ] 破坏性操作走 `confirmAction` 二次确认。
- [ ] 不留 `console.log`、注释掉的代码或 TODO（除非 TODO 里写了负责人）。
- [ ] 提交信息使用前缀 `feat:` / `ui:` / `ux:` / `fix:` / `hig:` / `docs:`，一项改动一个提交。

## 三、合入流程
1. 作者在群里报"分支 + 提交号 + 截图路径"。
2. 用户体验设计师按 `ux-plan.md` 验收流程，Apple 设计标准管理师做 HIG 复核，两人各回一句通过或不通过（附原因）。
3. Bug修复工程师重跑测试并合入 `master`，在群里报合并提交号。
4. 最高决策权抽查，不达标会直接打回，并写明要改什么。

## 四、优先级
P0（ux-plan 四项 + HIG P0）全部合入并通过验收后才开始 P1，P1 全部完成后再开始 P2。插队需最高决策权同意。
